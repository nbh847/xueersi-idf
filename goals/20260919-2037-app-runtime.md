# Goal：实现 App Framework 核心运行时

## 元信息

- 对应节点：节点 1“App Framework”
- 状态：待执行
- 前置条件：节点 0“构建基线恢复”已完成；施工文档为 `goals/20260919-1834-build-baseline.md`
- 后续目标：节点 2“Navigation”

## 目标与预期行为

在不改变现有 Hardware Dashboard 启动和操作行为的前提下，建立可被后续 Launcher 使用的 App Framework 核心运行时。框架应能注册 App、初始化已注册 App、打开一个 App、关闭当前 App，并准确维护当前生命周期状态。

本 Goal 不实现 Launcher、Navigation、页面栈、Games 页面、硬件迁移或任何新的用户界面。

## 背景与文件入口

- 当前业务入口为 `main/main.c` 的 `app_main()` 和 `lvgl_task()`，仍然直接创建 Hardware Dashboard。
- 目标接口和生命周期草案见 `docs/xiaomiao_firmware_v0.1_design.md` 第 5 节。
- 节点顺序、验收状态和下一步见 `ROADMAP.md`。
- 当前组件入口为 `main/CMakeLists.txt`，没有独立 `apps/`、`framework/` 或 `services/` 组件。

## 范围边界

允许修改：

- 新增 `main/framework/` 下的 App 类型、Registry、Manager 和开发自测代码。
- 修改 `main/CMakeLists.txt`，将新增框架源文件纳入 ESP-IDF `main` 组件。
- 修改 `main/main.c`，仅加入框架初始化和开发自测的最小接入点；不得重写现有 Dashboard。
- 新增或更新本 Goal、`ROADMAP.md`、`docs/project-overview.md` 和必要的设计说明。

禁止修改：

- Launcher、Navigation、Games、PC Monitor、Tools、Settings 等后续功能。
- `main.c` 中现有 LCD、按键、ADC、I2C、蜂鸣器、MicroSD 和 Dashboard 业务逻辑。
- `GD32_firmware/`、硬件协议、引脚定义和原理图。
- `dependencies.lock`、LVGL 版本和其他依赖版本。
- 未经确认的大规模目录迁移或新的 FreeRTOS Task。

## 已确定的实现决策

1. 第一阶段代码放在 `main/framework/`，继续作为现有 ESP-IDF `main` 组件的一部分，避免为了目录结构引入新的顶层组件。
2. App 描述保持设计文档中的核心字段：`id`、`name`、`icon`、`init`、`open`、`close`。回调使用 `void`，由框架 API 返回 `esp_err_t` 表示注册和状态错误。
3. Registry 使用固定容量的静态数组，容量设为 16；不使用堆分配，不拥有 App 描述或字符串的内存。注册顺序即枚举顺序，为后续 Launcher 提供稳定入口顺序。
4. `id` 必须非空且唯一，`name` 必须非空；`icon` 和生命周期回调允许为空并按空操作处理。重复 ID、无效描述和容量耗尽必须返回明确错误。
5. Manager 同时只允许一个当前 App。`init_all` 只执行一次；未初始化不能 `open`，已有当前 App 时不能直接打开另一个 App；`close` 在无当前 App 时保持幂等。
6. 本阶段不实现导航栈、App 间切换和线程安全。框架 API 只在现有 LVGL 任务或启动初始化路径调用，后续 Navigation Goal 再决定并发边界。
7. 开发自测通过 CMake 选项 `XIAOMIAO_FRAMEWORK_SELF_TEST=ON` 启用，默认构建不得包含自测代码或改变产品启动日志。

## 执行检查点

### 检查点 1：接口与错误语义

- 定义 `xiaomiao_app_t`、Registry API、Manager API 和生命周期状态。
- 明确 `esp_err_t` 返回值：无效参数、重复 ID、容量耗尽、未初始化、当前 App 冲突和未找到 App。
- 为空回调、重复调用和所有权规则写出注释或接口文档。

预期结果：后续 Launcher 可以只依赖头文件，不接触 GPIO、SPI、I2C 或 LVGL 对象。

### 检查点 2：Registry 实现

- 实现清空、注册、数量、按索引读取和按 ID 查找。
- 覆盖空 ID、空名称、重复 ID、超过 16 个 App 和注册顺序。
- 不引入动态内存或新的第三方依赖。

预期结果：注册表行为确定，返回的 App 描述指针在框架生命周期内保持有效。

### 检查点 3：Manager 生命周期

- 实现 `init_all`、`open`、`close` 和当前 App 查询。
- 验证初始化只调用一次，打开和关闭回调顺序正确。
- 验证未初始化打开、重复打开、切换冲突、关闭后再次打开和空回调路径。

预期结果：任意时刻最多一个当前 App，关闭后状态恢复为空，后续 Navigation 可以在此基础上实现切换。

### 检查点 4：开发自测与构建接入

- 新增最小测试 App 和生命周期计数器，仅在 `XIAOMIAO_FRAMEWORK_SELF_TEST=ON` 时编译。
- 自测必须覆盖两个 App 注册、重复 ID 拒绝、初始化一次、打开/关闭顺序、当前 App 冲突和最终空闲状态，并输出唯一的 `APP_FRAMEWORK_SELF_TEST: PASS` 标记。
- 普通构建不启用自测；现有 Dashboard 仍由 `app_main()` 启动。

预期结果：自测失败时构建或运行明确失败，不能静默跳过；普通固件不增加自测行为。

### 检查点 5：回归验证与交付

- 执行普通构建，确认 ESP-IDF 6.1 构建通过。
- 使用独立临时构建目录启用自测选项并构建、烧录，串口出现 `APP_FRAMEWORK_SELF_TEST: PASS`。
- 再烧录普通固件，确认 Dashboard 仍能启动、15 页可翻页，A/B 键行为不变。
- 更新 `ROADMAP.md` 和本 Goal 的检查点、验证结果及限制。

## 失败路径与处理要求

- App 描述不完整或 ID 重复：拒绝注册并保留已有 Registry，不自动修正或覆盖。
- App 数量超过容量：返回容量错误，不能静默丢弃；如确需扩大容量，先更新设计决策和验收范围。
- 生命周期回调顺序错误：保持 Goal 未完成，补充计数器证据后再修复；不得通过放宽断言绕过。
- 自测选项污染普通固件：检查 CMake 缓存和编译宏，必要时使用全新 `.tmp/` 构建目录复现。
- Dashboard 回归失败：停止后续节点，先定位框架接入对启动顺序或 LVGL 任务的影响。
- 无法烧录自测固件：可以完成静态构建检查，但不得将生命周期运行自测标记为通过，并需明确未验证范围。

## 验收标准

- [ ] 框架代码位于 `main/framework/`，并纳入现有 `main` 组件。
- [ ] Registry 支持静态注册、按序读取、按 ID 查找和重复 ID 拒绝。
- [ ] Manager 支持初始化、打开、关闭和当前 App 查询，任意时刻最多一个当前 App。
- [ ] 空回调、非法状态、容量边界和重复操作均有确定结果。
- [ ] 普通构建不启用自测，现有 Dashboard 启动与交互未改变。
- [ ] 自测构建覆盖两个 App 的生命周期和失败路径，并输出 `APP_FRAMEWORK_SELF_TEST: PASS`。
- [ ] 普通构建和自测构建均通过 ESP-IDF 6.1 编译。
- [ ] 自测固件烧录后串口通过，普通固件烧录后 15 页翻页及 A/B 键回归通过。
- [ ] 未修改 GD32、硬件协议、依赖版本或 `dependencies.lock`。
- [ ] `git diff --check` 通过，Goal 和 `ROADMAP.md` 已记录证据与未验证范围。
