## 目标与预期行为

建立独立的 Wi-Fi Service，使设备具备首次配网、凭据持久化、开机自动连接、断线重连、扫描和状态查询能力。没有凭据、附近没有网络、密码错误或网络中断时，固件仍须继续进入 Launcher，不得阻塞硬件、LVGL 或 App Framework 启动。

首次配网使用“设备开启受密码保护的临时热点，用户用手机打开本地网页”的方案。用户不需要安装 App、连接电脑或在掌机六键界面输入密码。新 SSID 和密码只有在设备实际连接成功并取得 IPv4 地址后才能替换原凭据；保存成功后，普通重启和断电重启均能恢复。

在屏幕右上角增加全局 Wi-Fi 状态图标，覆盖 Launcher、Games、PC Monitor、Tools、Settings 和 Hardware Test。图标表达是否连接、连接过程和四档信号强度；SSID、IP、错误原因等详细信息放在 Tools／Settings 的 Wi-Fi 页面。

## 已确认的用户流程

### 首次配网或更换网络

1. 用户进入 `Settings → Wi-Fi`，选中 `Configure` 并按 A。
2. 设备启动临时 SoftAP，屏幕显示：

   ```text
   SSID: Xiaomiao-XXXX
   Password: 8 位随机数字
   Open: http://192.168.4.1
   B Cancel
   ```

3. 用户在手机上连接该热点。手机如果自动弹出配网页则直接使用；没有弹出时，在浏览器访问 `http://192.168.4.1`。
4. 网页扫描并列出附近 Wi-Fi。用户选择目标 SSID、输入密码并提交。
5. 设备使用新凭据试连：
   - 成功取得 IPv4：保存新凭据，关闭配网网页和临时热点，屏幕显示已连接状态。
   - 认证失败、找不到 AP 或超时：不得覆盖旧凭据；临时热点和网页继续可用，显示明确错误并允许重新提交。
6. 用户按 B、配网空闲超时或进入关闭流程时，停止配网并释放 SoftAP、HTTP、DNS 和扫描资源。

### 后续启动

- `wifi_auto_connect=true` 且存在有效凭据：异步连接已保存网络。
- `wifi_auto_connect=true` 但没有凭据：进入 `NO_CREDENTIALS`，继续启动 Launcher，不反复空连。
- `wifi_auto_connect=false`：初始化 Wi-Fi 能力但不自动连接；用户仍可手动进入 Settings 配网。
- 保存成功的凭据在普通重启、断电重启和不擦除 NVS 的普通固件更新后继续有效。
- 擦除整片 Flash、清空 NVS 或执行明确的 `Forget network` 后，凭据不再存在。

### 忘记网络

1. 用户在 `Settings → Wi-Fi` 选中 `Forget network`。
2. 页面进入确认态，A 确认、B 取消。
3. 确认后断开当前连接并删除已保存凭据；不得清除 Settings、其他 NVS key 或整个 NVS 分区。
4. `wifi_auto_connect` 偏好保持原值；没有凭据时即使该值为 `true`，也只进入 `NO_CREDENTIALS`。

## 总体架构

```text
Settings App ── 配网／开关／忘记 ─┐
                                  ├── Wi-Fi Service ── ESP-IDF Wi-Fi／Netif／Event
Tools App ───── 只读状态查询 ─────┤          │
                                  │          ├── 临时 SoftAP + DNS + HTTP 配网页
Framework Wi-Fi Indicator ────────┘          └── Wi-Fi 凭据持久化

Settings Service ── wifi_auto_connect ───────► Wi-Fi Service
```

职责约束：

- Wi-Fi Service 不依赖 LVGL、Navigation、Launcher 或具体 App。
- App 只能调用 Service 公开接口，不得直接调用 `esp_wifi_*`、`esp_netif_*`、HTTP Server 或 NVS API。
- 全局图标属于 Framework UI，只读取 Service 状态，不拥有网络生命周期。
- ESP-IDF 事件回调不得直接调用 LVGL。UI 在 LVGL 线程读取快照并更新对象。
- 配网页只采集凭据，提交后交给 Service 试连和保存。

```c
typedef enum {
    XIAOMIAO_WIFI_UNINITIALIZED = 0,
    XIAOMIAO_WIFI_DISABLED,
    XIAOMIAO_WIFI_NO_CREDENTIALS,
    XIAOMIAO_WIFI_DISCONNECTED,
    XIAOMIAO_WIFI_SCANNING,
    XIAOMIAO_WIFI_CONNECTING,
    XIAOMIAO_WIFI_RETRY_WAIT,
    XIAOMIAO_WIFI_CONNECTED,
    XIAOMIAO_WIFI_PROVISIONING,
    XIAOMIAO_WIFI_AUTH_FAILED,
    XIAOMIAO_WIFI_ERROR,
} xiaomiao_wifi_state_t;
```

公开快照至少包含：

```c
typedef struct {
    xiaomiao_wifi_state_t state;
    bool auto_connect;
    bool has_credentials;
    bool provisioning_active;
    char ssid[33];
    int8_t rssi;
    uint8_t signal_level;

    uint32_t retry_count;
    esp_err_t last_error;
    uint8_t last_disconnect_reason;

```

约束：

- `signal_level` 取值为 `0～4`；未连接时必须为 `0`。
- 快照不得包含 Wi-Fi 密码、临时热点密码、HTTP 表单内容或内部指针。
- `get_snapshot()` 复制完整快照，状态与字段必须来自同一时刻的受保护数据。
- 未连接时清空旧 IP 和旧 RSSI，不能出现 `CONNECTED` 但数据来自旧连接的撕裂状态。
- Service 初始化失败后仍提供可读的 `ERROR` 快照。

## 凭据持久化决策

### 存储边界

- SSID 和密码使用 ESP-IDF Wi-Fi 的 Flash-backed 配置存储机制保存在默认 NVS 中。
- Wi-Fi Service 明确区分“待验证凭据”和“已提交凭据”。待验证凭据只存在于内存。
- 提交网页表单后，Service 使用 RAM 存储路径试连；只有收到对应连接的 `IP_EVENT_STA_GOT_IP` 后，才切换到 Flash-backed 存储并提交同一组凭据。
- 若试连失败、用户取消或超时，清理待验证凭据并恢复旧连接策略；Flash 中旧凭据保持不变。
- 实施时必须按 ESP-IDF 6.1 的实际 API 约束核对 `esp_wifi_set_storage()`、`esp_wifi_set_config()`、启停顺序与错误返回。若运行态不能安全切换存储，允许封装等价的私有凭据存储适配器，但仍必须满足“取得 IP 后才提交”和“失败保留旧凭据”，不得退化为表单提交即覆盖。

### 数据生命周期与安全边界

- 启动时只把非空、长度合法的保存配置视为有效凭据。
- SSID 最大 32 字节；密码按 ESP-IDF 支持范围校验，网页端和 Service 端均拒绝超长或非法输入。
- 保存、读取、忘记均不得打印密码；涉及缓冲区使用后应清零。
- `Forget network` 只能清理 Wi-Fi 配置，不得擦除默认 NVS 分区。
- 项目当前未启用 Flash Encryption／NVS Encryption，因此不得声称凭据可抵抗拆机读取。安全边界是：不经 UI／日志泄漏，配网链路由临时 WPA2 热点保护；物理 Flash 攻击不在本节点范围内。

## 配网热点与网页

### SoftAP

- 配网期间使用 `WIFI_MODE_APSTA`，成功或退出后回到 STA 模式。
- SSID 为 `Xiaomiao-XXXX`，后缀取设备 MAC 末两字节并使用大写十六进制。
- 每次会话用硬件随机源生成新的 8 位数字密码。
- 安全模式为 WPA2-PSK；不得开启无密码热点。
- 最大客户端数为 1，默认地址为 `192.168.4.1`。
- 空闲超时为 10 分钟；超时后自动关闭并回到原状态。
- 成功、B 取消、Service 关闭或异常回滚时，停止 SoftAP 并释放资源。

### 网页

- 提供 DNS 通配解析，尽量触发手机系统 captive portal；自动弹窗是便利能力，不作为唯一入口。
- 屏幕始终显示确定性入口 `http://192.168.4.1`。
- 页面只包含扫描／刷新、SSID 列表、密码输入、连接按钮、进度和错误。
- 扫描结果按 RSSI 从强到弱排序，相同 SSID 去重，首版最多显示 10 个可见网络。
- 网页不得回显已保存密码，不提供读取原密码接口。
- HTTP 请求体设置明确上限，拒绝超长字段、缺失 SSID、非法 Content-Length 和并发提交。
- 配网成功后返回成功页，再关闭 HTTP、DNS 和 SoftAP。

## 连接与重连策略

### 开机连接

1. 初始化网络栈、默认事件循环、STA netif 和 Wi-Fi 驱动。
2. 读取 `wifi_auto_connect` 与已保存凭据状态。
3. 无凭据或自动连接关闭时立即返回，不等待网络。
4. 满足条件时调用异步连接并返回，Launcher 继续启动。

### 断线重连

- 非用户主动断开且 `wifi_auto_connect=true` 时，按 `1、2、5、10、30` 秒退避重连，之后保持 30 秒间隔。
- 成功取得 IP 后重试计数和退避恢复初始值。
- 用户关闭自动连接、主动断开、忘记网络或切换凭据时，取消待执行重连。
- 密码／认证失败进入 `AUTH_FAILED`，停止高频重试，等待重新配网。
- AP 暂时消失、信标超时等可能恢复的错误使用退避重连。
- DHCP 未取得 IP 时按连接超时处理，不得永久停在 `CONNECTING`。
- 初始化和连接错误记录原始错误并进入可查询状态，不使用 `ESP_ERROR_CHECK` 终止普通启动。

## 全局右上角 Wi-Fi 图标

### 所有权与布局

- 新增 Framework 级 Wi-Fi Indicator，挂载在 LVGL top layer 或等价全局顶层对象上，不属于任何 App 内容根。
- 图标固定在右上角，目标占用约 `10 × 10 px`，不得新增整行状态栏或压缩主体布局。
- 图标不接收输入，不改变 LVGL group 焦点，不参与 Navigation 对象所有权。
- Launcher 和各 App 标题为右上角预留空间；逐页检查标题、页码、Hardware Test 装饰元素与图标不存在重叠。
- Indicator 通过 LVGL timer 在 UI 线程读取 Service 快照；状态变化最迟 500 ms 内反映到图标。
- 连接成功后，Service 每 5 秒读取一次当前 AP RSSI；不得用持续扫描获取 RSSI。

### 四档信号强度

| RSSI | 档位 | 图形 | 颜色 |
| --- | --- | --- | --- |
| `≥ -55 dBm` | 4 | 四格亮起 | 绿色 `#4CAF50` |
| `-56 ～ -67 dBm` | 3 | 三格亮起 | 绿色 `#4CAF50` |
| `-68 ～ -75 dBm` | 2 | 两格亮起 | 黄色 `#FFC107` |
| `< -75 dBm` | 1 | 一格亮起 | 橙红色 `#FF7043` |

### 非连接状态

| 状态 | 图形 | 颜色 | 行为 |
| --- | --- | --- | --- |
| 正在连接／重连 | 四格依次循环 | 蓝色 `#42A5F5` | 约 500 ms 一步 |
| Wi-Fi 已开启但未连接 | 四格空心 | 浅灰色 `#9E9E9E` | 静态 |
| Wi-Fi 已关闭 | 四格空心加 `×` | 深灰色 `#616161` | 静态 |
| 连接失败 | 空格加 `!` | 红色 `#EF5350` | 显示约 3 秒后回到未连接 |

图例：

```text
绿色  ▂▄▆█   已连接，信号强
绿色  ▂▄▆░   已连接，信号良好
黄色  ▂▄░░   已连接，信号较弱
橙红  ▂░░░   已连接，信号很弱
蓝色  ▂▄▆█   正在连接，四格循环变化
浅灰  ░░░░   Wi-Fi 已开启但未连接
深灰  ░░░░×  Wi-Fi 已关闭
红色  ░░░░!  连接失败，短暂提示
```

颜色不是唯一信息通道。格数、循环、`×` 和 `!` 必须同时存在，使黑白显示、色觉差异或强光环境下仍能区分状态。弱信号使用橙红色，纯红色只用于实际连接失败。

## Settings 与 Tools 页面

### Settings → Wi-Fi

```text
Wi-Fi
Status         Connected / Not connected / ...
Auto connect   On / Off
Configure
Forget network
B Back
```

- 上下键移动焦点，边界停止；A 执行当前项；B 返回或取消确认／配网流程。
- `Auto connect` 必须先通过 Settings Service 成功持久化，再通知 Wi-Fi Service 应用。
- 保存失败时保持原值并显示错误，不得只改 UI。
- 从 `On` 切到 `Off` 时取消自动重连并断开当前连接；Wi-Fi 能力保持初始化。
- `Configure` 进入配网状态页，显示 SoftAP 信息和 B 取消提示。
- `Forget network` 必须二次确认。
- 页面退出不能隐式断开成功的 STA 连接；处于配网流程时 B 才停止配网会话。

```text

Status    Connected

```

- 每次进入读取真实快照；打开期间最多每 1 秒刷新，退出后删除 timer。

- 无凭据、自动连接关闭、认证失败和内部错误使用可区分的真实文案。

- Wi-Fi Service 可以创建网络栈需要的系统资源，但不得等待扫描、关联、DHCP 或重连完成。
- 任何 Wi-Fi 错误都不能阻止 LCD、LVGL、Launcher 和 Hardware Test 初始化。
- Framework／Navigation／Launcher／Settings Service 自测构建保持原边界。
- 若新增 Wi-Fi 专项自测，必须与已有自测选项互斥，不得真实保存或删除用户凭据。

## 并发、资源与日志要求

- ESP event loop 回调只更新内部状态、安排重连或提交轻量事件，不执行 LVGL 操作和长时间 HTTP 处理。

- 重复调用初始化、开始／停止配网、断开和忘记必须结果可预测，不重复注册 handler 或泄漏 netif、timer、Task、Socket。

## 失败路径与处理要求

- 网络栈或事件循环已创建：识别合法已存在状态，不重复创建或误判为致命错误。
- Wi-Fi 驱动初始化失败：状态为 `ERROR`，记录原始错误，继续 Launcher。
- 无保存凭据：状态为 `NO_CREDENTIALS`，不视为故障，不自动开启配网热点。
- 扫描失败：网页显示失败并允许重试；不得破坏正常 STA 连接或旧凭据。
- 表单非法：返回明确的 4xx 响应，不进入连接状态。
- 密码错误：状态为 `AUTH_FAILED`，不提交新凭据，不高频重连。
- AP 不存在或暂时离线：使用退避重连；UI 显示未连接／重连中。
- DHCP 超时：退出永久 `CONNECTING`，进入可恢复失败或重连状态。
- 新凭据保存失败：不得报告配网完成；显示“已连接但未保存”，重启恢复旧凭据。
- Forget network 失败：保留 `has_credentials=true` 和原状态，不假装已删除。
- 配网热点启动失败：回滚 HTTP／DNS／netif 资源并恢复原 STA 状态。
- 手机断开热点：等待重新连接，直到用户取消或 10 分钟超时。
- 图标创建失败：网络 Service 继续工作；记录 UI 错误，不重启设备。

### 2. 凭据存储：按 goal 的“私有适配器”分支实施

核对 ESP-IDF 6.1（`components/esp_wifi/include/esp_wifi.h`、`esp_wifi_types_generic.h`、`examples/protocols/http_server/captive_portal`）后确认两点：

1. `esp_wifi_set_storage()` 的文档只说明默认值为 `WIFI_STORAGE_FLASH`，没有任何运行态切换保证；`WIFI_STORAGE_FLASH` 下 `esp_wifi_set_config()` 会立即把 STA 配置写入默认 NVS 的 `nvs.net80211` 命名空间。
2. 因此“试连时存 RAM、取得 IP 后改存 Flash”无法依赖驱动自身的存储切换。

实施采用 goal 允许的等价方案：**Wi-Fi 驱动全程 `WIFI_STORAGE_RAM`**，凭据由 Service 自己持久化到默认 `nvs` 分区的私有 key `xiaomiao/wifi_creds`，格式为固定宽度版本化 blob（schema v1，104 字节：2 字节版本、2 字节 payload 长度、SSID 长度、密码长度、2 字节保留位、32 字节 SSID、64 字节密码）。写入前校验、`nvs_commit()` 成功后才替换内存快照；`Forget network` 只调用 `nvs_erase_key()` 删除该 key，源码中不存在 `nvs_flash_erase()`，也不修改分区表。

两条硬性约束因此仍然成立：试连凭据只存在于 RAM；密码错误、找不到 AP 或超时都不会覆盖已保存网络。

### 3. 状态机与计时器

- 状态迁移由 Wi-Fi／IP 事件驱动，事件回调只更新受互斥锁保护的状态、安排重连或提交轻量事件，不调用 LVGL。
- 计时器共四个：重连退避（1／2／5／10／30 秒，之后维持 30 秒）、连接超时（20 秒，避免永久停在 `CONNECTING`）、配网收尾（成功取得 IP 后 50 ms 关闭热点与网页，保证 HTTP 响应先回到手机）、RSSI 采样（每 5 秒读取关联 AP，不用扫描）。
- 配网会话的空闲超时为 10 分钟，HTTP 请求与 AP 客户端连断都会重置倒计时。
- 锁顺序固定：`get_snapshot()` 先复制快照并释放 Service 锁，再读取配网会话标志，两把锁从不同时持有。

### 6. 分区表调整（已确认，最终为自定义分区表）

本节点触发了一次分区表重划，经过三步：

1. 原始状态：IDF 默认 `partitions_singleapp.csv`，app 分区 1 MB，加 Wi-Fi 前固件 702,304 字节。

最终布局（`partitions.csv`，ESP-IDF `gen_esp32part.py` 校验通过）：

| 分区 | 类型 | 偏移 | 大小 | 说明 |
| --- | --- | --- | --- | --- |
| nvs | data/nvs | 0xA000 | 24 KB | 与之前完全相同，Settings 与 Wi-Fi 凭据不受影响 |
| phy_init | data/phy | 0x10000 | 4 KB | 不变 |
| factory | app | 0x20000 | **2 MB** | 当前 1359 KB，余量约 690 KB，覆盖节点 11～15 的加代码需求 |
| assets | data/spiffs | 0x220000 | **1.5 MB** | 预留给节点 15 的字体/图标/音效资源；在节点 15 落地前保持未使用、不挂载，因此完全无害 |

### 8. 实机首轮发现：内部 DMA 内存不足（2026-09-21）

人工烧录后首次启动崩溃：

```text
assert failed: lvgl_display_init main.c:1404 (buf3)
```

**根因**：LCD 走三块全屏 DMA 缓冲，每块 160 × 128 × 2 = 40,960 字节，共 120 KB，且必须来自内部 RAM（ESP32 的 SPI DMA 不能寻址 PSRAM）。Wi-Fi 驱动与 `wpa_supplicant` 初始化后占用同一内部内存池，第三块缓冲分配失败，原有代码用 `assert(buf3)` 直接中止启动。

**处理（两处，互补）**：

1. `sdkconfig.defaults` 增加 `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y`：让 Wi-Fi 与 LWIP 的缓冲优先分配在 PSRAM，先把内部 RAM 还给显示子系统。本项目网络流量很小，接受的代价是 Wi-Fi 吞吐略降。该选项依赖已启用的 `CONFIG_SPIRAM_USE_MALLOC=y`。
2. `main.c` 的 `lvgl_display_init()` 改为**运行时降级**：第三块缓冲分配失败时不再中止，而是退到「双缓冲 + 全屏刷新」路径并打一条 WARN，日志与 Hardware Test 的 About 页改为显示实际获得的缓冲数（新增 `s_lcd_draw_buf_count`）。前两块缓冲仍然是硬断言——它们失败说明内存已经不足以驱动屏幕，此时停机才是正确行为。配置宏 `LCD_DRAW_BUF_COUNT` 仍为 3，内存允许时行为与改动前完全一致。

**边界说明**：这是节点 10 引入 Wi-Fi 后的连带修复，改动落在 `main.c` 的显示初始化与 `sdkconfig.defaults`，没有触及引脚、外设协议或 Dashboard 的页面逻辑。

**验证状态**：已实机确认（2026-09-21）。启动日志显示 `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y` 生效（Wi-Fi 先于显示初始化完成），但第三块缓冲仍然拿不到，`lvgl_display_init()` 按预期降级并打警告：

```text
W (1811) xiaomiao_dash: third draw buffer unavailable (40960 bytes), falling back to two-buffer refresh
I (1811) xiaomiao_dash: LVGL display: 160x128, dpi=60, 2 full-screen DMA buffers, SPI=60 MHz
I (1844) xiaomiao_dash: Launcher ready, 5 app(s) registered
```

**已确认的取舍（2026-09-21，项目负责人）**：接受双缓冲，不再为第三块缓冲继续调参。依据：一帧 40 KB 在 60 MHz SPI 上约 5.5 ms，一帧预算 16.7 ms，双缓冲的下限 `max(渲染, 传输)` 约 5.5～6 ms，余量接近 3 倍；且本屏 TE 引脚未接 MCU，无法垂直同步，三缓冲换不来抗撕裂，只为吸收渲染抖动。代价是 40 KB 稀缺内部 RAM，正与 Wi-Fi 争夺同一内存池。

保留“尝试分配第三块、失败则降级”的自适应写法：将来若内部内存宽裕（例如进一步压缩 Wi-Fi 缓冲），三缓冲会自动恢复，无需改代码。`LCD_DRAW_BUF_COUNT` 仍为 3，代表期望值而非保证值。

### 10. 首轮实机功能验证发现（2026-09-21）：配网启动失败

```text

```

**根因**：`esp_wifi_set_config(WIFI_IF_AP, ...)` 要求当前 Wi-Fi 模式**已经包含 AP**，否则返回 `ESP_ERR_WIFI_MODE`。原实现把 `esp_wifi_set_config()` 放在 `esp_wifi_set_mode(WIFI_MODE_APSTA)` 之前，顺序反了。

**修复 1（顺序）**：`session_start()` 改为「创建 AP netif → 切到 `WIFI_MODE_APSTA` → 写 AP 配置」。切模式会重启驱动并断开当前 STA 连接，这一点已在注释中说明，且由收尾时的 `station_reconnect_saved()` 负责恢复。

**修复 2（连带发现）**：切到 APSTA 触发的 STA 断开事件会被原有逻辑判为「可恢复断线」，进而启动对**旧网络**的退避重连——在用户正在挑选新网络时只会制造噪声，还会把状态从 `PROVISIONING` 顶掉。现在 `handle_station_disconnected()` 在配网会话活跃期间（且非试连提交路径）只把状态维持在 `PROVISIONING`，不安排重连；会话结束时统一恢复已保存网络。

**验证状态**：两处修复均未重新烧录验证。

### 13. 取消配网后的多余断连（2026-09-21，已修未复测）

在设备已连上 Wi-Fi 的状态下进入 `Configure` 再按 B 取消，日志显示：

本来健康的连接被主动切断，白等一次 20 秒连接超时再加 1 秒退避才恢复，用户会经历约 22 秒断网。

`reason 15` 是 4 次握手超时。第一次配网也有同样现象（前两次 join 失败，第三次才成功连上），当时被忽略。

**根因 1（主因）**：SoftAP 被固定配置在信道 6，而设备 STA 关联的 AP 在**信道 1**。APSTA 模式下驱动强制 AP 跟随 STA 信道，于是手机刚加入就遭遇一次信道切换并掉线。

修复：会话启动时读取 STA 当前信道（`esp_wifi_sta_get_ap_info()` 的 `primary`）并用它配置 AP，未关联时回退到信道 1。在 `set_mode(APSTA)` **之前**读取，否则 STA 已被断开。这样通道从头就是一致的，不再发生切换。

**根因 2（次因）**：默认的 `WIFI_PS_MIN_MODEM` 省电会让射频周期性休眠，AP 响应变慢时手机侧就会握手超时。修复：会话期间 `esp_wifi_set_ps(WIFI_PS_NONE)`，收尾（`session_stop` 与回滚路径）恢复 `WIFI_PS_MIN_MODEM`。

**根因 3（带宽）**：日志显示手机以 `bgn, 40U`（40 MHz）关联热点。配网热点只需要兼容性、不需要吞吐，因此会话期间显式设为 `WIFI_BW20`（`esp_wifi_set_bandwidth(WIFI_IF_AP, WIFI_BW20)`）。注意 IDF 6.1 的枚举名是 `WIFI_BW20`，旧版的 `WIFI_BW_HT20` 已不存在。

**诊断修正（重要）**：复盘更早一次配网的日志后发现，**当时 STA 并未关联（`sta:<0,0>`），AP 始终在信道 6、没有发生信道切换，手机仍然连续两次 `reason = 15`**（第三次才成功）。因此"信道切换"只解释了**已关联 STA 时的掉线**，不能解释全部现象；三种因素（信道切换、省电、40 MHz 关联）叠加，本次一并处理，但**各因素的实际权重尚未确证**。复测时若仍有反复 join／leave，需要按新日志继续排查（下一步方向是手机侧行为与 AP 的 beacon／DTIM 参数）。

**顺带确认**：日志里的 `httpd_uri: URI '/generate_204' not found` 与 `/favicon.ico not found` 是**正常现象**——前者是 Android 的 captive portal 探测，后者是浏览器自带的图标请求；两者都由注册的 404 错误处理器兜底重定向到配网页，不影响功能。

**验证状态**：三处修复均未烧录复测；复测时应确认手机连上热点后不再出现 `reason = 15` 的反复 join／leave，网页可稳定打开，并继续完成「错误密码不覆盖旧凭据」这一项。

### 16. 更换网络实际不可用（2026-09-21，已修未复测）

在「错误密码不覆盖旧凭据」验证中，日志暴露出更严重的问题：

```text
W (166912) wifi:sta is connected, disconnect before connecting to new ap
I (166913) wifi_svc: trial connect started, ssid='CMCC-U2Tx'
W (186913) wifi_svc: connect attempt timed out before an IPv4 lease
W (186923) wifi_svc: trial connect failed, reason=8, saved network kept
```

**根因**：`esp_wifi_connect()` 在已有站点关联时会被驱动拒绝（只打印 `sta is connected, disconnect before connecting to new ap`），而试连路径**从未断开旧连接**。因此只要设备当前连着某个网络，`Configure` 提交就永远走不到连接，只能在 20 秒连接超时后失败。本次用户提交的恰好是同一个网络，所以现象只是"超时后恢复"；**若提交的是另一个网络，更换网络功能根本不可用**。

**修复**：

1. `xiaomiao_wifi_service_provision_connect()` 在配置试连凭据前先 `esp_wifi_disconnect()`，并轮询 `esp_wifi_sta_get_ap_info()` 直到关联消失（上限 1 秒），因为 `connect()` 在离开过程未完成时同样会被拒绝。
2. 新增 `s_trial_switching` 标志：这次主动断开产生的事件是**预期**的，不能被当成"试连失败"。在 `handle_station_disconnected()` 中，试连进行中且 `s_trial_switching` 为真、或断开原因是 `WIFI_REASON_ASSOC_LEAVE`（本次实测为 `reason=8`）时直接忽略。后者用于兜底事件晚到的时序——事件可能在标志清除之后才被处理。

**同一批日志已验证生效的修复**：

- 省电开关：`wifi:Set ps type: 0`（会话开始）→ `wifi:Set ps type: 1`（收尾恢复）。
- 带宽：首次关联由之前的 `bgn, 40U` 变为 `bgn, 20`。
- 退避重连：会话结束、STA 未关联时打印 `reconnect in 1 s (attempt 1)`，1 秒后自动连回 CMCC-U2Tx 并重新取得 `192.168.1.29`。
- 旧凭据保护：`trial connect failed ... saved network kept`，随后成功连回**原网络**，凭据未被覆盖。

**仍未解决**：手机首次关联热点仍失败一次（`reason = 15`），第二次成功。**该现象已于同日定位**：手机按 SSID 缓存了上一次会话的随机密码，而热点 SSID 固定为 `Xiaomiao-XXXX`、密码每次会话重新随机生成，因此首次关联必然握手失败（`reason = 15` 即 4-way handshake timeout）。这不是缺陷，而是"每次随机密码"这条安全要求与手机密码缓存叠加的必然结果，具体处置见第 17 条。

**验证状态（2026-09-21 已复测通过）**：日志显示试连前旧连接被主动释放（`wifi:state: run -> init (0x0)`），**不再出现** `sta is connected, disconnect before connecting to new ap`。提交另一个网络 `CMCC-5pu4` 后 **4.5 秒**内失败（`reason=2`，认证被拒）且 `saved network kept`；随后提交原网络 `CMCC-U2Tx`，**2.1 秒**内连上并 `credentials saved`。也就是说：换网络可用、错误凭据快速失败、旧凭据与自动重连均正常，三项同时得到证据。此前"试连超时 20 秒"的行为不复存在。

**仍待验证**：（已闭合，见下）

**换网持久化补验（2026-09-21 已复测通过）**：本轮以**正确密码**试连真正不同的网络 `CMCC-5pu4`（信道 6，bssid `b8:60:61:f4:3d:41`；与旧网络 `CMCC-U2Tx` 的信道 1、bssid `cc:29:bd:0a:69:ea` 完全不同），1.6 秒连上并 `credentials saved`；`rst:0x1 (POWERON_RESET)` 真断电重启后日志为 `saved network loaded, ssid='CMCC-5pu4'` → `connected with CMCC-5pu4` → 取得 IP，且 `Launcher ready`（1983 ms）仍早于取 IP（3644 ms）。由此"不同 SSID 换网 + 新凭据跨断电持久化 + 替换旧凭据"全部取得实机证据，「更换网络」功能闭合。上一轮 `CMCC-5pu4` 的 `reason=2` 失败由此反证确为错误密码所致。

### 17. 首次关联必败：定位与处置（2026-09-21，已确认保持现状）

**现象与定位**（由项目负责人指出，日志印证）：

```text
I (124756) join, bgn, 20        ← 手机用缓存的上一次密码发起关联
I (128763) leave, reason = 15   ← 4-way handshake timeout，即密码不匹配
I (140420) join, bgn, 40U       ← 重新输入屏幕上的新密码后成功
```

热点 SSID 固定为 `Xiaomiao-XXXX`，而密码每次会话由硬件随机源重新生成。手机按 SSID 缓存凭据，因此**每次配网，手机的第一次关联必然用旧密码失败一次**。`reason = 15` 正是这一行为的特征，不是链路质量问题——早前把它归因于省电与 40 MHz 已在本节点被排除。

**处置决定（2026-09-21，项目负责人）**：**保持现状**，不引入 SSID 随机后缀，也不把热点密码改为固定值。

理由：现状完全符合 Goal 的两条要求（SSID 为 `Xiaomiao-XXXX`；密码每次会话随机，从而保证只有能看到设备屏幕的人才能连入热点）。两个备选都要在这些要求上让步——SSID 加后缀偏离命名规定，密码固定则直接削弱安全边界；而换来的只是"少一次失败尝试"，收益不足以抵消让步。

**接受的行为**：每次配网时，若手机曾连接过本热点，首次关联会失败一次，需要重新输入设备屏幕上的新密码。这不是缺陷，记录在此以免后续重复排查。

**未采纳的低成本改善**（供后续参考）：在配网页加一行提示，例如"若手机提示连接失败，请重新输入设备屏幕上显示的新密码"。该改动只涉及文案、不影响安全模型，本次未做。
